WHY (planned in claude.ai, 2026-10-22)
  Overlord shouldn't do everything itself. A daily AI read is good at judgement and
  bad at timing: the Plex compromise (ticket 02) ran for five days before anyone saw
  it. So, three layers:
  1. PROBES: small deterministic scripts on systemd timers (minutes, not days), no AI,
     no cost. Each appends one JSON line per run to its own log and can raise an alert.
  2. OVERLORD's daily run reads the probes' last 24 h as summaries (plus everything it
     reads today) and writes the report.
  3. RECOMMENDATIONS: when overlord finds a root cause or a repeating pattern, it
     proposes automation (usually a new probe) in a structured field. Jay accepts or
     rejects; an accepted one becomes a ticket, built by Claude Code as now. Overlord
     still changes nothing itself and still runs with no tools.

ALERT ROUTING (Jay, 2026-10-22: "probes can alert on their own, but by default route
through overlord for summarization")
  - route "summarize" (default): the alerter starts an off-schedule overlord run in
    alert mode. Claude gets the alert, the probe's last 2 h of lines and a fresh
    collector run, and writes a focused report; the email subject starts
    "[overlord] ALERT". Capped at 4 alert runs per day (each costs one run, ~$0.12).
    If the cap is reached, or the run fails or times out, the alerter falls back to
    a direct email, so an alert is never lost.
  - route "direct": the alerter emails the alert itself at once (probe, severity,
    findings, time, "overlord will cover this in the morning report"). For probes
    where speed matters more than prose, or as the fallback above.
  - Probes never hold secrets: a probe only writes an alert file into a spool
    directory. Only the alerter (as sysai) can read the Gmail and API credentials.
  - De-duplication: the same probe + check is alerted at most once per hour (state
    in the probe); a check that clears and returns after 1 h alerts again.

PROBE ACCOUNTS (Jay agreed 2026-10-22; why, for README.md)
  Each probe runs as its own system account with nothing else attached
  (overlord-probe-<name>: no home, no shell, no password, no groups except
  overlord-alerts). Benefits:
  - A probe can't read sysai's API key or Gmail password, or anything in /home.
  - A buggy or exploited probe can only damage its own state and log files.
  - Each probe gets only the permissions its own checks need, written in its unit
    file where they can be reviewed, instead of every probe getting root.
  - ps, the journal and file ownership show which probe did what.
  Why not systemd's DynamicUser (throwaway uids): DynamicUser forces a private /tmp,
  so the intrusion probe couldn't see the real /tmp, the first place the Plex attack
  wrote to. A static account with the same lockdown gives the benefits without that.

THE INTRUSION PROBE (every 2 min; what would have caught the Plex attack on day one)
  Checks, each a finding with check name, severity and detail:
  1. exe_in_tmp (critical): a process whose executable is in /tmp, /var/tmp, /dev/shm,
     or shows "(deleted)".
  2. miner_proxy (critical): process command lines matching known miner / proxy
     patterns (xmrig, minerd, "stratum+tcp", "--donate-level", myawesomeproxy; list in
     intrusion.conf, matched case-insensitively).
  3. tmp_executable (critical): an executable file in those directories owned by a
     system account (uid 1-999 or nobody). Same rule as the collector's security
     section; move that logic into probes/lib.sh and have collect/uba5.sh use it
     (collect/uba5.sh is listed; keep its output unchanged).
  4. unexpected_outbound (critical): established TCP to outside the LAN by a uid not in
     OUTBOUND_OK_USERS; also any connection to common pool ports (3333, 4444, 5555,
     7777, 14444, 45700, list in conf). Counts and ports only; no outside addresses in
     the log or the alert.
  5. plex_back (critical): plexmediaserver active, the package installed, or processes
     as user plex (until Jay's apt purge, this fires: start it as warn while the package
     is installed and the unit inactive; critical if anything runs).
  6. cpu_hog (warn): a process not in CPU_OK over 80 % CPU for 3 checks in a row.
  7. new_listener (warn): a listening TCP/UDP port not in the baseline (taken by
     install.sh into the probe's state dir; Jay re-takes it with a documented command
     after adding a service).
  Each run writes one line to /var/log/overlord/probes/intrusion.jsonl:
    {"ts","probe":"intrusion","severity":"ok|warn|critical","findings":[...],
     "metrics":{"load1","procs","outbound_by_user":{...},"listeners":N},"ms":N}
  Everything in "findings" passes through overlord-redact first (command lines can hold
  secrets). Keep 14 days (the probe trims its own log once a day). A run takes well
  under 2 s; log a warning in its own line if it takes over 10 s.
  Permissions (unit file, reviewed in Stage 0): User=overlord-probe-intrusion,
  AmbientCapabilities and CapabilityBoundingSet = CAP_SYS_PTRACE (read /proc/<pid>/exe
  of other users' processes) and CAP_DAC_READ_SEARCH (list directories an attacker
  locked down in /tmp), NoNewPrivileges=yes, ProtectSystem=strict, ProtectHome=yes,
  InaccessiblePaths=/etc/shadow /etc/gshadow /etc/sudoers /etc/sudoers.d /root
  /home/sysai, PrivateTmp=no (it must see the real /tmp), PrivateDevices=yes,
  ProtectKernelTunables=yes, ProtectControlGroups=yes, RestrictSUIDSGID=yes,
  StateDirectory=overlord-probes/intrusion, LogsDirectory=overlord/probes,
  ReadWritePaths= the alert spool only. CAP_DAC_READ_SEARCH can read any file, which is
  why ProtectHome and the InaccessiblePaths above matter: the probe must not be able to
  read any secret on uba5. Stage 3 proves it.

REGISTRY AND RECOMMENDATIONS
  probes/registry.json: [{"name":"intrusion","interval_s":120,"account":
  "overlord-probe-intrusion","route":"summarize","log":
  "/var/log/overlord/probes/intrusion.jsonl","purpose":"..."}]. The collector and the
  prompt use it, so overlord knows what already exists and doesn't recommend it again.
  report.schema.json: add "recommendations": array (may be empty) of
    {"ref": existing id or "", "title" (<=100), "kind": "probe"|"fix"|"ticket",
     "target_repo": "overlord"|"cookie-cam"|"other", "frequency": "" or e.g. "2 min",
     "why" (<=400, the evidence), "check" (<=400, what it would test and when it would
     alert)}.
  The runner keeps /home/sysai/runs/recommendations.json: id R-1, R-2, ...; state
  proposed | accepted | rejected | done; first_seen, last_seen, times_seen; Jay's note.
  A ref to an existing id updates it; no ref adds a new one. The prompt gets every
  recommendation with its state and note: never re-propose a rejected one unless there
  is new evidence, and then say what is new.
  overlord-rec.py (Jay runs: sudo -u sysai /usr/local/lib/overlord/overlord-rec.py ...):
  list, show R-n, accept R-n, reject R-n "note", done R-n. Prints the next ticket's
  title for an accepted one; it writes no tickets itself.
  Email: new recommendations listed under the report. Site: recommendations.html (all,
  by state) and probes.html (each probe: last run, stale?, last 24 h by severity,
  alerts sent and how). Probe findings and recommendations are summaries; raw probe
  lines are not published (same rule as the collector's facts).
